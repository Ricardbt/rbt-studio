Case Study — RBT Studio

SDD Harness

Un wizard de 5 fases para que Claude Code y yo hablemos el mismo idioma antes de escribir una línea de código.

Cliente — Side project / interno Rol — Diseño y desarrollo del skill Timeline — Desde mayo 2026, en uso activo
Claude Code Skill Specification-Driven Development Multi-agente TDD
F.01 — CONTEXTO

El problema

Cada proyecto nuevo con Claude Code arrancaba distinto: unas veces directo por el código, otras con una spec improvisada. El resultado era siempre el mismo — specs inconsistentes de un proyecto a otro, y una desconexión entre lo que yo tenía en la cabeza y lo que los agentes acababan construyendo.

Los skills de planificación estructurada que probé no encajaban: los simples no tenían fondo real detrás de la plantilla, y los completos estaban pensados para equipos grandes — mucha ceremonia, poca agilidad para un proyecto propio o de cliente mediano.

F.02 — PROCESO

Cómo se abordó

La decisión clave fue tratarlo como un sistema Lean, no como gestión de proyectos disfrazada de skill: un wizard de 5 fases, cada una con una responsabilidad concreta cuya salida alimenta a la siguiente.

01Spec
02Architect
03Scaffold
04Harness Agents
05Handoff

El ancla del sistema es TDD: cada fase de implementación exige tests que pasen antes de darse por buena. Es la diferencia entre "creo que esto cumple la spec" y "esto cumple la spec porque los tests lo confirman".

F.03 — SOLUCIÓN

Qué se construyó

Un skill de Claude Code que se invoca al arrancar cualquier proyecto o feature, y guía la conversación por las 5 fases de forma secuencial, generando en cada una los artefactos correspondientes — specs, decisiones de arquitectura, estructura de proyecto — antes de tocar código de implementación.

Ya se ha usado para arrancar proyectos reales: la PRD completa de Job Search OS salió de este proceso, pivotando de un CRM manual a un Career Operating System event-driven con una arquitectura más sólida de la que habría salido empezando directo por el código.

F.05 — APRENDIZAJES

Qué se aprendió

La estructura correcta no estaba ni en la plantilla mínima ni en el proceso exhaustivo, sino en un sistema Lean con fases bien delimitadas y una única disciplina no negociable — TDD — que hace de ancla. Más fases habrían reintroducido la fricción que se quería evitar; menos disciplina de tests habría vuelto al punto de partida: buenas intenciones sin verificación real.
